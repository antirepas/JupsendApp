JUPSEND / EMAILTRACKER — SENDING MECHANISM CONTEXT
====================================================
Use this document as background when discussing sending limits and realistic daily output for this product.


WHAT THE PRODUCT IS
-------------------
jupsend (emailTracker) is a self-hosted cold-email / outreach app. Each user connects one Gmail account via OAuth. Outbound mail goes through Gmail (SMTP XOAUTH2 or Gmail API raw send). The app tracks opens, clicks, and replies; supports one-shot campaigns, A/B tests, and behavior-based workflow sequences (waits, open/click branches, follow-ups). There is one sending profile per user (one Gmail inbox).


HOW SENDING WORKS (SHORT SUMMARY)
---------------------------------
When a user launches a campaign, schedules a send, or a workflow step fires, the app does not send email inline in the HTTP request. It creates an email_sends row (delivery_status=queued) and a matching send_jobs row (status=pending), then wakes a background outbound worker. The worker picks pending jobs, checks that the user's Gmail account is active and under rate limits, renders the template with contact variables, injects tracking pixel and link rewrites, and delivers via Gmail. On success the job is marked sent and the account's sends_today counter increments. If rate-limited, the job is rescheduled (typically seconds to minutes; if the daily cap is hit, until midnight). Transient SMTP/API errors retry with backoff; permanent errors (bad mailbox, auth failure) fail immediately and may suppress the contact. Workflow follow-ups also enqueue send_jobs the same way — workflows never bypass the queue or rate limits.


END-TO-END PIPELINE
-------------------
1. TRIGGER
   - User launches campaign (manual or scheduled every 30s scheduler)
   - Workflow engine enqueues a send when a workflow hits an "send email" step (scheduler every 45s, or immediately on open/click events)
   - User sends a one-off test email via API/UI (higher priority)

2. ENQUEUE (outbound/enqueue.go)
   - Requires a "send-ready" Gmail profile (active OAuth, configured SMTP host)
   - Skips suppressed contacts, invalid emails
   - Campaign bulk enqueue also skips: contacts in send cooldown (default 30 days since last sent), contacts already in another active/draft campaign
   - Creates email_sends + send_jobs, links them, notifies worker

3. WORKER (outbound/worker.go)
   - Runs continuously: default tick every 3 seconds (+ immediate wake on new jobs)
   - Claims up to OUTBOUND_MAX_CONCURRENT jobs (default 16), but only ONE job per user at a time in a batch
   - Per-user mutex: sends for the same user are serialized through the worker
   - Before send: AccountCanSendNowForJob() checks daily cap, per-minute cap, and spacing
   - If blocked: RescheduleSendJob with delay (1s–midnight depending on reason)
   - If allowed: executeJob() → Gmail API or SMTP, mark sent, increment counters

4. POST-SEND
   - Campaign marked "sent" when no active jobs remain for that campaign
   - Workflow instance context updated with last_send_id; workflow may advance on next scheduler tick
   - IMAP poller (default every 3 minutes) checks inbox for bounces and replies


SENDING PROFILE (smtp_accounts)
---------------------------------
One row per user. Key fields:

  daily_limit              Hard ceiling per calendar day (default 50)
  per_minute_limit         Max sends in any rolling 60s window (default 2)
  min_seconds_between_sends Minimum gap between sends (default 30 seconds)
  warmup_enabled           On by default (1)
  warmup_daily_cap         Starting daily cap when warmup begins (default 5)
  warmup_target_daily_cap  Ramp target (default 50)
  warmup_increment_per_day Daily increase during warmup (default 5)
  warmup_started_at        Set when Gmail is first connected
  sends_today              Counter reset at calendar day boundary
  last_send_at             Used for spacing enforcement

Configured in Settings → Sending limits (Gmail-connected users only).
New Gmail OAuth connections get PostgreSQL column defaults (not hardcoded in app code).

IMPORTANT: daily_limit and warmup_target_daily_cap are related but separate.
  - EffectiveDailyCap() is what actually gates sending.
  - With warmup ON: cap ramps from warmup_daily_cap (+ increment each day) up to warmup_target_daily_cap, never above daily_limit.
  - With warmup OFF: EffectiveDailyCap = daily_limit immediately (no ramp).

Example warmup timeline at defaults (5 start, +5/day, target 50):
  Day 0: 5/day, Day 1: 10, ... Day 9: 50, then stays at 50.
  At target 500 with same increment: ~99 days to reach full cap.

User outreach goal (goal_daily_send_cap on users table) is ONLY for dashboard math ("required reply rate to hit meeting goal"). It does NOT enforce sending.


RATE LIMIT ENFORCEMENT (outbound/ratelimit.go, router.go)
---------------------------------------------------------
All limits are per SMTP account (per user). A send is allowed only if:

  1. account.status == "active"
  2. sends_today < EffectiveDailyCap(account)
  3. sends in last 60 seconds < per_minute_limit (default 2; falls back to 2 if 0)
  4. min_seconds_between_sends elapsed since last_send_at (default 30s)
     - Exception: manual one-off sends (priority >= 10) skip spacing check but still hit daily + per-minute limits

When daily cap is exhausted:
  - Worker reschedules jobs until next local midnight (calendar day reset on sends_today_reset_at)

Per-minute tracking is IN-PROCESS MEMORY (minuteMap in ratelimit.go).
  - README notes: run a single app instance for correct per-minute throttling unless shared rate-limit storage is added.
  - Daily counter is in PostgreSQL and is correct across restarts.


REALISTIC THROUGHPUT MATH (APP-SIDE)
------------------------------------
Defaults: daily cap 50, 2/min, 30s spacing, warmup on ramping to 50.

Per-minute + spacing both cap at ~2 emails/minute = ~120/hour theoretical.
Daily cap 50 is usually the binding constraint before minute/spacing limits.

Time to drain a full daily quota at default pacing:
  50 sends ÷ 2/min ≈ 25 minutes of continuous sending (if queue is full)

If daily_limit raised to 500 with same 2/min and 30s spacing:
  500 ÷ 2/min ≈ 250 minutes (~4.2 hours) to exhaust quota
  Minute/spacing still cap burst rate; worker won't blast 500 instantly.

Worker concurrency (default 16) helps multiple users in parallel, but each user is limited to one in-flight job and one Gmail account.

Maximum attempts per job: 5. Backoff on transient errors: 15s, 1m, 5m, 15m, 60m.


JOB PRIORITIES
--------------
  PriorityManual (10):   One-off / test sends — skip spacing, shorter rate-limit reschedule (1s or 15s)
  PriorityCampaign (0): Campaign and workflow sends — full spacing enforced


CAMPAIGN TYPES
--------------
  simple:     One template (optional A/B), all contacts enqueued at launch
  ab:         Variant A/B per contact at enqueue time
  workflow:   Starts workflow instances per contact; each send step enqueues a job
  workflow_ab: A/B on first workflow send only; follow-ups use mapped templates

Scheduled campaigns: checked every 30 seconds; due campaigns call same launch path as manual.


WORKFLOW SENDING
----------------
Workflow scheduler runs every 45 seconds, claims up to 50 due instances.
Send steps call the same EnqueueSend() path as campaigns (not direct SMTP).
Open/click events can wake waiting instances immediately for branch logic.
Workflow sends count against the same daily/minute/spacing limits as campaigns.
A contact in a workflow receiving starter + 3 follow-ups = 4 separate send_jobs on potentially different days (depending on wait nodes and rate limits).


ELIGIBILITY & DELIVERABILITY GUARDRAILS (APP-SIDE)
--------------------------------------------------
Before enqueue:
  - Suppressed contacts (hard bounces) skipped
  - Invalid email_status skipped
  - Send cooldown: default 30 days since last successful send to same contact
  - Cannot add contact to new campaign if already in another draft/sending campaign

After failed send:
  - Permanent mailbox errors may auto-suppress contact
  - IMAP bounce detection correlates via X-EmailTracker-Send-ID header

These reduce duplicate/blind sends but do NOT replace ISP/Gmail reputation limits.


GMAIL / EXTERNAL LIMITS (NOT ENFORCED BY APP)
---------------------------------------------
The app throttles to protect reputation, but Gmail/Google impose their own caps:
  - Consumer Gmail: often cited ~500 emails/day for regular mail, but cold outreach typically throttled much lower based on reputation, spam reports, bounces
  - Google Workspace: higher limits for established senders; still reputation-dependent
  - New domains / fresh OAuth connections: sending 500/day immediately (warmup off) risks blocks, spam folder, or OAuth errors

The product can CONFIGURE 500/day; Gmail may not DELIVER 500/day to inboxes if reputation is poor.


ENVIRONMENT KNOBS (outbound/config.go)
--------------------------------------
  OUTBOUND_WORKER_INTERVAL     default 3s
  OUTBOUND_BATCH_SIZE          default 10 (candidate jobs fetched; claim logic uses MaxConcurrent)
  OUTBOUND_MAX_CONCURRENT      default 16 parallel send goroutines
  OUTBOUND_LOCK_SECONDS        default 45s job processing lock
  OUTBOUND_SMTP_TIMEOUT_SECONDS default 30s
  IMAP_POLL_INTERVAL           default 180s (3 min)


QUEUE STATES
------------
send_jobs:     pending → processing → (complete | failed | dead)
               rate-limited jobs stay pending with future scheduled_at
email_sends:   queued → sending → sent | failed

Ops endpoint /api/v1/ops/queue (admin): global pending/sent/failed/dead counts.
